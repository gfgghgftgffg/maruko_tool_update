# 更新与 release 维护

## 上游更新

检查官方 x264、t_mod_New 的原始提交和扩展差异，更新 lock 中提交、开发包地址、SHA256 与 DLL 列表。不要对有本地修改的 vendor 强制 reset；需要时在新 checkout 中构建。prepare 在提交不匹配时会报错。

确认 patches 可应用。FFmpeg API 变更时修复相关输入或滤镜代码，不退回旧库来冒充更新。保持源码 Git 历史，避免版本号变成 x 或错误的修订号。

分别构建并验证所需位深。FFmpeg 的可执行程序不等于开发库；x264 编码核心的更新也不等于替换小丸 ffmpeg.exe。

## 发布前验收

- 检查 EXE 与全部非系统 DLL 依赖链；8bit/10bit 各自验证。
- 小丸副本中检查默认与自定义参数、字幕、缩放、音频、进度、取消和批量。
- 已知缺口明确列出；未补齐时以候选或 pre-release 发放。
- 不宣称未测量的画质、速度或压缩率改善。
- ZIP 包含 tools、说明、manifest、许可证和必要的上游构建信息、补丁；公开源码项目提供准确依赖和构建方法，并满足上游源码分发要求。
- 随包保留上游构建信息及本项目补丁；提供明确的对应源码访问方式。GPLv3 第 6(d) 条允许源码放在其他服务器，但下载页面须给出清楚指引，维护者仍负责确保源码可获取。来源网站链接不能代替对应源码链接，FFmpeg full 构建所需第三方组件也需核对。
- 检查 manifest、文件哈希和最终归档 SHA256。

## release 约定

ZIP 名为 `maruko_tool_update-x264-x64-8bit-<x264版本>-ffmpeg-<FFmpeg版本>-<日期>.zip`，10bit 类似；EXE 始终保留原名称。

构建脚本只生成归档。维护者完成验收后创建 GitHub release 并上传资产，版本说明列出更新组件、覆盖清单、验证和限制。

不强制把上游源码放进主仓库或每个工具 ZIP。可以采用明确的、版本固定的第三方源码链接；也可以提供独立对应源码归档。选择链接方式时，确保内容对应、可获取，并包含所需修改与构建资料。

增加 x265 或 32 位时，分别维护依赖、覆盖清单和验收，不能把未实现内容标为支持。FFmpeg 的其他小丸调用路径需要逐项验证，不能把音频处理测试视为全部功能兼容。
